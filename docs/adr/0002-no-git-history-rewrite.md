# ADR 0002：不改写 git 历史来清除已泄露的 webhook

- 状态：已接受（Accepted）
- 相关提交：main 合并提交 `0e5cf3a`（PR #10）；`archive/v1` 为该提交的完整快照；
  本批次在 `refactor/archive-v1` 分支
- 相关：SECURITY.md、CHANGELOG.md、[ADR 0001](0001-from-prediction-to-evidence.md)、
  `.security-allowlist.json`、ARCHIVE.md

## 背景

【事实】git 全历史扫描（CI `fetch-depth: 0`）发现同一个飞书 webhook 值在至少 3 个提交、
4 次 diff 中重复出现，且只有 1 个不同的凭据值；已逐条登记在 `.security-allowlist.json`，
状态为 `revoked`（已撤销），登记条目保留。当前 HEAD 无该值。

【事实】该 webhook 已由所有者于 2026-11-05 确认在飞书侧轮换并停用，历史 URL 不再有效；
轮换由所有者执行，仓库 / agent 未代做（见 SECURITY.md）。

【事实】第一批改造刚建立起以 commit sha 为坐标的证据链：`CLAIMS.json`、`SECURITY.md`、
`CHANGELOG.md`、ADR 0001、`docs/VALIDATION_V2_2026-10-06.md`、`.security-allowlist.json`
均引用具体 commit sha 与历史值。

【推断】是否改写 git 历史，是「视觉上的干净」与「证据链完整」之间的治理取舍，
而不是一次单纯的技术清理动作。

## 决策

【推断】**不改写 git 历史**来清除已泄露的 webhook。改用检测、显式登记、CI 阻断新增、
公开记录，并配合由所有者在飞书侧完成的轮换（见「替代处置」）。三条论证：

1. 【推断】改写历史不能让已泄露的凭据失效。公开仓库的 fork / clone / 缓存 / CI 日志
   可能已持有该值；只有飞书侧轮换 / 停用该 webhook 能让凭据失效，而该处置已由所有者
   于 2026-11-05 完成。改写只改变本仓库的视图，不改变凭据在外部是否仍有效；既然凭据
   已因轮换失效，改写历史在凭据有效性上没有任何增量收益。
2. 【推断】改写会摧毁本项目刚建立的证据链。`CLAIMS.json`、`SECURITY.md`、`CHANGELOG.md`、
   ADR 0001、`docs/VALIDATION_V2_2026-10-06.md`、`.security-allowlist.json` 都引用具体
   commit sha 与历史值；改写后所有 sha 失效，结论无法再定位到唯一代码版本——这恰好是
   项目自身要防的错：结论与产生结论的代码版本脱钩。把自身的证据链纪律用在自己身上，
   意味着治理记录所引用的坐标不能被自己抹掉。
3. 【推断】公开仓库改写历史会破坏所有既有 clone，属于对第三方的破坏性操作；收益
   （视觉上的「干净」）远小于成本（协作者本地历史失效、引用断裂、需强制同步）。

## 后续状态更新（2026-11-05）

【事实】所有者于 2026-11-05 确认该 webhook 已在飞书侧轮换并停用：唯一有效处置已完成，
凭据不再有效，历史 URL 失效。本仓库未执行该动作，也未改写 git 历史。

【事实】凭据失效不等于 git 历史中的明文值被清除：该值仍可通过全历史检出 / fork /
缓存 / CI 日志取回；当前 HEAD 工作树无该值。本决策不声称该值已从历史移除。

【事实】不改写历史的决策**维持**：轮换完成后，改写现在连「促使轮换」的间接价值都不再
具备，收益进一步降低；论证②③不受影响，论证①在凭据有效性上更无增量收益。

【事实】`.security-allowlist.json` 三条登记的状态由 `recorded-pending-rotation` 更新为
`revoked`（已撤销），但登记条目与 `audit/secrets.py` 的 `feishu_webhook` 检测规则均保留：
历史 diff 仍含该值，需登记才不会让 CI 误阻断，同时保留检测以捕获同类新命中。

## 替代处置（已采用）

【事实】本批次实际落地的是以下组合，而非历史改写：

- 全历史扫描（`fetch-depth: 0`）发现重复命中；
- 逐条显式登记 allowlist（commit / path / rule / reason / status），状态 `revoked`
  （已撤销），条目与检测规则保留，不静默放行；
- CI 阻断任何新的未登记命中；
- `SECURITY.md` 公开记录事件、处置与责任边界；
- 轮换已由所有者于 2026-11-05 在飞书侧完成，历史 URL 不再有效；本仓库未执行该动作。

## 后果

### 正面

- 结论台账、治理文件与 allowlist 引用的 commit sha 继续有效，结论仍可定位到唯一代码版本。
- 既有 clone 不受影响；处置过程本身可审计（登记条目 + CI 门禁 + 公开记录）。
- 与项目「把证据链纪律用在自身」的动机一致，不制造新的 provenance 缺口。

### 负面

- 【事实】历史 diff 中的明文字符串仍可取回（全历史检出、fork、缓存、CI 日志），但它已不是
  有效凭据；本决策不声称该值已从历史清除。
- 【待确认】是否曾被非授权调用，仓库与所有者均未提供调用日志核查结果，无法判断。
- 【事实】allowlist 条目保留用于登记历史 diff，状态已更新为 `revoked`。

## 备选方案

### 方案一：git filter-repo 改写历史

用 filter-repo 清除历史中的 webhook 值并重写全部 commit。

否决：不能让已泄露凭据失效（决策论证 1）；会使治理文件引用的 sha 全部失效、结论与代码版本
脱钩（论证 2）；破坏所有既有 clone（论证 3）。收益仅为视觉上的干净，轮换完成后更无收益。

### 方案二：彻底删库重建

删除公开仓库，以干净历史重新推送。

否决：同样不能让外部已持有的凭据失效；会丢失全部 issue / PR / 提交历史与治理记录，
破坏范围最大，且与「保留历史证据」的原则直接冲突。

### 方案三：保留并显式登记（所选）

保留历史，全历史扫描 + 逐条登记 + CI 阻断新增 + 公开记录 + 飞书侧轮换（由所有者完成）。

理由：唯一有效处置已由所有者完成，仓库职责限于检测、登记、留痕与阻断新增；仓库让事件
可检测、可定位、可审计、不再新增。代价见「负面」。

## 依据

- 【事实】全历史扫描命中数、登记的提交 / 状态（现为 `revoked`）、当前 HEAD 无该值、
  治理文件引用 commit sha、本批次未改写历史、该 webhook 由所有者于 2026-11-05 在飞书侧
  轮换并停用（非本批次执行、本仓库未代做）：来源为仓库文件与 CI 配置
  （`.security-allowlist.json`、`SECURITY.md`、`CHANGELOG.md`、`CLAIMS.json`、
  `docs/VALIDATION_V2_2026-10-06.md`、ADR 0001、`.github/workflows/`）、git 历史与
  所有者确认。
- 【推断】三条决策论证、三选一的否决判断与「视觉干净收益小于成本」均为基于上述事实的
  工程判断，不是测量或验证结果。
- 【待确认】该 webhook 的调用日志是否已被核查、是否曾被非授权调用；是否另有本仓库与
  allowlist 之外的泄露渠道。仓库与所有者均未提供该信息。

## 边界：事实 / 推断 / 待确认

- 【事实】可由仓库文件、CI 配置、git 对象与所有者确认核对的陈述：重复命中与登记状态
  （`revoked`）、当前 HEAD 无该值、治理文件引用具体 sha、本批次未改写历史、该 webhook
  已由所有者于 2026-11-05 在飞书侧轮换并停用（非本批次执行）；git 历史中的明文值仍可取回。
- 【推断】基于事实的解释与价值判断：改写不能使凭据失效、改写会摧毁证据链、
  改写对第三方是破坏性操作、三选一的取舍理由。
- 【待确认】需所有者或外部系统核对后才能定论的事项：该 webhook 的调用日志是否已被核查、
  是否曾被非授权调用；是否存在本仓库与 allowlist 之外的泄露渠道。仓库与所有者均未提供
  该信息，不予推断。

【待确认】该 webhook 的调用日志是否已被核查、是否曾被非授权调用；是否另有未登记的泄露
渠道；仓库与所有者均未提供该信息，不予推断。
